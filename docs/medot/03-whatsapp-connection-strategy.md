# Medot — WhatsApp Connection Strategy

Status: **Decided (product owner, 2026-11-01)** — Me. connects **exclusively**
through the official WhatsApp Agent Platform. Baileys, the Cloud API, and a
Medot-owned shared business number are **not** transports for Me. The
comparison tables below are retained as a historical record of the Stage 1
evaluation that informed — and was then overridden by — this decision.

Requirement recap: **one** WhatsApp conversational identity (Me.) per user;
specialist identities never appear on WhatsApp; proactive outbound (daily
messages) must work.

---

## 1. Decision (supersedes the Stage 1 recommendation)

**Medot's Me. agent connects exclusively through the official WhatsApp Agent
Platform.** The user creates/connects the agent through WhatsApp's **Agent
Manager** and supplies the API key generated by WhatsApp; Medot stores that
credential in the OS keystore and communicates with the user through the
dedicated agent conversation.

Consequences adopted with the decision:

- One agent conversation per user; internal specialist identities remain
  in-app (unchanged — the platform model fits Medot's identity design
  natively).
- The `Transport` abstraction (§4) remains, but with a single planned
  implementation. Its purpose is testability and future-proofing, not
  multi-transport switching.
- The Baileys sidecar and Cloud API adapter from AIA are **retired from the
  Medot roadmap** (not deleted from history; not ported into `runtime/`).

## 2. Prerequisites that gate implementation (must be verified before the WhatsApp milestone)

1. **Developer access.** As of 2026-11-01 there is no public Meta developer
   documentation or self-serve registration for third-party agent providers —
   the consumer "Agents" UI is rolling out (seen in Pakistan), but the
   provider-side "Agent Manager" onboarding is not publicly documented.
   **Action (spike, first item of the WhatsApp milestone): confirm the
   developer-side registration path and capture the actual API surface
   (messaging endpoints, webhooks, key scopes) from whatever access is
   granted.**
2. **Relay service (first Medot server component).** The Agent Platform is
   Meta-relayed: agent messages reach the provider's HTTPS endpoint — a
   desktop-only product cannot receive them directly. Medot requires an
   always-on cloud relay that receives platform webhooks, queues them
   per-user, and delivers to the user's desktop runtime over a persistent
   outbound connection (the user's machine never opens inbound ports).
   Message bodies must not be retained beyond delivery/ack. **This is an
   infrastructure and cost commitment requiring explicit authorization
   before build-out** (OD-13).
3. **Proactive outbound semantics.** How the platform treats agent-initiated
   messages (daily briefs) must be confirmed during the spike — the old
   24-hour-window/template rules applied to the Cloud API; Agent Platform
   rules are undocumented.

## 3. Historical record — Stage 1 evaluation (superseded)

The Stage 1 evaluation compared (a) Agent Platform, (b) Cloud API, (c) Baileys
on a dedicated companion number, (d) Baileys on the user's primary number, and
provisionally recommended (c). Key verified facts that remain true and
relevant background:

- `fromMe` semantics (verified in Baileys source): `fromMe=true` covers every
  send from the account — primary phone, any linked device, or the client
  itself; the standard skip-fromMe bot pattern is fatal on a primary-number
  session. (Moot under the Agent Platform decision.)
- Cloud API number exclusivity, 24-h window/template rules, per-message
  pricing (service messages re-charged Oct 2026; 1,000 free/month per number).
- The centralized-number analysis (§6 below) remains the best available
  reference for the **relay architecture** the Agent Platform decision now
  requires: multi-user identification, offline desktop queueing, persistent
  outbound desktop connections, and privacy constraints carry over directly.

## 4. What must be true for the transport layer

- Companion logic, identity state, and history live **only** in Medot
  (Supabase + local spool); nothing WhatsApp-side is load-bearing.
- `Transport` interface: `pair/connect (agent-link via API key)`,
  `send(peer, text)`, `on_inbound(handler)`, `health()` — normalized envelope
  (id, peer, text, timestamp, direction).
- Both the relay and the desktop side pass the same contract tests (inbound
  dedupe, outbound retry, reconnect-after-kill, offline replay).

## 5. Trigger points to revisit

- **Spike outcome**: if developer-side access cannot be obtained, the decision
  returns to the product owner with the relay + access findings.
- **Agent Platform GA changes** (pricing, webhook model, proactive-message
  rules) — revalidate the relay design at WhatsApp milestone start.

## 6. Relay-architecture reference (from the centralized-number analysis)

The centralized-number analysis below was written before the Agent Platform
decision, but its **relay column is now load-bearing**: the Agent Platform is
likewise Meta-relayed, so every routing/queueing/privacy row applies to the
chosen transport. Kept as the design reference for the Medot relay service
(OD-13).

| Concern | Meta-relayed platforms (Agent Platform; historically: one shared Cloud API number) |
|---|---|
| Onboarding | Best possible: user just messages the published Medot number — no QR, no SIM purchase. Account linking = verify ownership of that WhatsApp account (e.g. confirm a code Medot sends) |
| Multi-user identification | Inbound webhook carries the sender `wa_id` (per-user); Medot maps `wa_id → user_id` after verification. One conversation per user — fits the "one WhatsApp identity" model exactly |
| Outbound / proactive | 24-h customer-service window per user; **outside it only pre-approved templates** — daily briefs must ship as utility templates (Meta approval per template + per-category pricing). Service messages re-charged Oct 2026 with 1,000 free/month **per number — shared across ALL users**, a hard scaling ceiling |
| Message routing to the user's runtime | Requires a **Medot-operated relay**: cloud webhook receiver → per-user fan-out → the user's desktop runtime over a persistent outbound connection (desktop dials out; no inbound ports). Offline desktops need server-side queueing with replay + TTL, and the relay must never store message bodies beyond delivery (privacy) |
| Infrastructure | Always-on cloud service (webhook + queue + relay auth) — the product's first server component, with 24×7 availability expectations; a real cost and ops commitment the desktop-only MVP avoids |
| Privacy / isolation | Multi-tenant number: Meta sees one traffic pattern; tenant isolation enforced in the relay; risk of cross-user routing bugs is a new failure class that local-only transports don't have |
| Costs & limits | Per delivered message (1,000 free service msgs/month per number), 250-recipient tier initially; template approvals add review latency for every new proactive message type |
| Policy | Fully official — no ToS risk, no ban exposure |

**Trade-off summary (historical)**: the centralized number won decisively on
onboarding friction and policy safety, and lost on: a mandatory always-on
relay service (first server component), template constraints on proactive
messages, shared free-tier limits, and new multi-tenant routing/privacy
failure modes — the same relay commitment the Agent Platform decision now
carries (see §2.2).

**Status**: DECIDED (§1). Implementation is gated on the two prerequisites in
§2; the relay design must be prototyped and authorized (OD-13) before the
WhatsApp milestone begins.

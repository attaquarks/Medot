AIA — Two-Agent Local Assistant: Architecture Specification

A production-oriented design for independent agents running locally and orchestrating via asynchronous system events.

Deliverable status: a coherent, runnable scaffold (93 files) + this specification. Infrastructure, agent framework, schema, provider abstractions, Docker stack and onboarding are real and wired together; remaining integration calls are marked TODO(impl) with exact contracts.

The Two Agents

AIA splits core functional domains into two fully independent AI agents. The agents share only the infrastructural baseline, implementing distinct prompts, toolboxes, database namespaces, and memory structures.

Agent 1

Business Assistant

A lightweight executive assistant designed to handle client WhatsApp communication, monitor and triage incoming emails, manage complex scheduling/availability loops via Google Calendar, track project tasks, initiate interactive phone sessions, and record CRM metadata with proactive daily briefs.

Agent 2

Health & Diet Coach

A personal accountability and fitness coach. Translates unstructured food inputs ("2 eggs, toast and tea") directly into caloric metrics, tracks systemic physical KPIs (weight logs, targeted exercises), computes baseline TDEE dynamically, reports unhealthy lifestyle anomalies, and pushes weekly diagnostic progress updates.

Every external trigger becomes an event on Redis Streams; agents are configured as consumers inside dedicated named consumer groups to guarantee at-least-once delivery. The ingress gateway routes each inbound message to its absolute destinatary (whatsapp.inbound.business or whatsapp.inbound.health) avoiding response collisions.

Hybrid LLM Routing

The platform relies on smart operational routing logic. By treating local computation as the logical default and delegating to cloud resources only when necessary, operational expenditures and network risks are heavily minimized.

Smart Execution Policy

The system evaluates incoming user messages and context. If a strict mathematical evaluation, structured JSON transformation, or deep reasoning task is identified (or if LLM_FORCE_CLOUD=1 is passed), the request is intelligently forwarded to the cloud engine. If cloud tokens are unavailable or disconnected, the system automatically runs 100% offline inside the local device boundary.

  • Local Default: ollama/llama3.1:8b

    Private, free, high-speed execution handling over 80% of routine task classification, tool calls, and daily state queries.

  • Cloud Fallback: gpt-4o-mini / Claude

    Reserved dynamically for complex multi-parameter calendar scheduling, hard context extractions, and critical error-recovery pipelines.

Isolated Data Model

Physical security boundaries are preserved via strict database schema layout definitions within PostgreSQL. Row-Level Security (RLS) guards multi-tenant workloads.

Schema: core

Manages master tenant structures, encrypted connection parameters, conversation graphs, operational audit histories, and global vector search embeddings (pgvector 768-dimension vectors).

Schema: business

Contains tenant-isolated tables holding rich CRM customer details, historical email collections, live calendar schedules, pending actions, and telephone interaction logs.

Schema: health

Enforces physical isolation of fitness accounts. Records macro-nutrient nutrition profiles, dietary timelines, precise body mass indicators, activity indices, and dynamic target caloric ranges.

Double-Layered Memory Partitioning

To preserve operational latency boundaries, the agent's memory is divided into two distinct computational layers:

  • Short-Term Layer: Instantaneous sliding transaction windows cached in Redis. Formatted uniquely as (tenant_id:agent_id:channel_peer) to prevent information cross-contamination during active conversation turns.
  • Long-Term Layer: Vector similarity querying performed inside Postgres. System searches are scoped using database constraints on (tenant_id, agent) matching, ensuring complete workspace privacy.

Security Framework

AIA is designed around a hardened, zero-trust cryptographic layer protecting individual developer keys and personal profile details from unauthorized memory scraping.

Zero Plaintext Storage

Credentials undergo envelope encryption. A robust Master Key retrieved from the OS system keychain decrypts row-specific keys on-the-fly, locking out unauthorized DB dumps.

Secure OAuth Loops

Utilizes server-mediated OAuth 2.0 flows with state parameters. Sensitive user access tokens are locked in the server space; client-side exposure is prevented entirely.

Action Verification

Agents utilize complete write access within safe limits. Destructive actions, high-capital events, or critical deletions escalate directly to the human principal for manual signature.

Immutable Audit Logs

All tool activities record structural append-only logs. Custom scrubbing logic runs synchronously prior to disk storage, stripping tokens, credentials, and sensitive markers.

Scalability Vector

The code architecture is designed to scale horizontally without modifications to core agent schemas. A local laptop installation can seamlessly transition into a highly available multi-tenant cloud application:

1. Personal Setup (Default Mode)

Runs directly within standard localized machines, pinning tasks to the default tenant space with zero routing overhead.

2. Shared Private Instances

Operates inside dedicated host machines serving small internal teams. Tenant partitions operate natively on top of standard schema structures.

3. Distributed Multi-Tenant SaaS

Utilizes headless stateless container farms coupled to managed DB clusters, relying on hardware security KMS vaults and official Meta cloud integrations.
